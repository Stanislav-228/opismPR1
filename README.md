### A.3. Запит до служби доменних імен

У Windows замість `dig` використовується `Resolve-DnsName`.

**Команда (перше виконання):**

``` powershell
Resolve-DnsName example.com -Type A
```

**Вивід:**

``` text

```

**Команда (повторне виконання через 5--7 хвилин):**

``` powershell
Resolve-DnsName example.com -Type A
```

**Вивід:**

``` text
[ВСТАВИТИ ПОВНИЙ ФАКТИЧНИЙ ВИВІД ПОВТОРНОГО ЗАПИТУ]
```

  Параметр                 Перше виконання   Повторне виконання
  ------------------------ ----------------- --------------------
  Час виконання (год:хв)   \[вказати\]       \[вказати\]
  IPv4-адреса              \[вказати\]       \[вказати\]
  Значення TTL (сек.)      \[вказати\]       \[вказати\]

TTL --- це час у секундах, протягом якого DNS-запис може зберігатися в
кеші. Під час повторного звернення значення зазвичай зменшується; якщо
кеш оновився, воно може зрости.

**1. Скільки рядків діагностичного виводу передує отриманню даних

відповіді. **Результат: \[вказати кількість рядків за власним логом\].**

**2. Які рядки наявні у виводі A.1 і відсутні у виводі A.2? Чим це
зумовлено?**

У A.1 для HTTPS мають бути повідомлення, пов'язані з TLS: узгодження
параметрів захищеного з'єднання, перевірка сертифіката та встановлення
TLS-каналу. У A.2 використовується звичайний HTTP, тому TLS-етап не
виконується. Остаточний перелік рядків слід звірити з обома фактичними
виводами.

**3. Звідки у виводі з'явилося значення `443`, якщо його не було вказано
в адресі?**

Для HTTPS стандартним портом за замовчуванням є `443`. Якщо порт не
зазначено в URL, `curl.exe` використовує його автоматично.

**4. Як змінилося значення TTL між двома запитами (A.3)? Що означає це
число?**

Фактичні значення: **\[TTL першого запиту\] → \[TTL повторного
запиту\]**. TTL --- це час у секундах, протягом якого DNS-запис може
залишатися в кеші. Зазвичай залишок зменшується з часом; після оновлення
кешу значення може збільшитися.

## Висновки

Під час цієї практичної роботи розглядається послідовність етапів, які
відбуваються під час звернення клієнта до вебресурсу. Для домену
`example.com` потрібно простежити перетворення доменного імені на
IP-адресу, встановлення транспортного з'єднання, узгодження захищеного
каналу HTTPS, надсилання HTTP-запиту та отримання відповіді сервера.
Кожен із цих етапів відображається окремими діагностичними
повідомленнями `curl.exe`.

Для власної моделі виділено п'ять груп: визначення мережевої адреси,
транспортне з'єднання, захищений канал TLS, формування HTTP-запиту та
отримання прикладного ресурсу. Такий поділ дає змогу розглядати процес
послідовно --- від пошуку вузла до отримання даних. Кількість груп можна
було б змінити, якби фактичні повідомлення показали, що певні етапи
доцільно об'єднати або розділити.

Порівняння HTTPS і HTTP дає змогу побачити, що захищене з'єднання
містить додатковий етап TLS, якого немає у звичайному HTTP. Перевірки
ресурсів BadSSL демонструють три різні причини недовіри до сертифіката:
завершення строку дії, невідповідність імені вузла та самопідписання.
Повторні DNS-запити потрібні для порівняння IP-адреси й TTL та
спостереження за роботою кешу.

**Перед здачею потрібно доповнити висновки конкретними спостереженнями з
власних логів:** зазначити фактичну зміну TTL, один неочікуваний рядок
із виводу та питання, яке виникло під час експерименту. Ці деталі не
можна достовірно встановити без реальних результатів виконання команд.

## Примітки виконавця

У Windows 11 команди виконуються в PowerShell. Для HTTP-запитів слід
використовувати `curl.exe`, оскільки `curl` у PowerShell може бути
псевдонімом іншої команди. Для DNS-запитів використовується
`Resolve-DnsName` замість `dig`.
